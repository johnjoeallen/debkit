# network.dns

The most complex module. Only `provider: dnsmasq` is declaratively managed — writing
an authoritative local zone plus upstream forwarding into a DebKit-owned dnsmasq
conf.d file. This is the fix for local names getting forwarded to public resolvers and
coming back NXDOMAIN. `/etc/resolv.conf` itself is **never written** here: it's
normally dynamically regenerated by NetworkManager/systemd-resolved, so rewriting it
directly would just get silently overwritten on the next reconnect. When the resolver
path doesn't point at dnsmasq, that surfaces as a standing diagnostic finding instead —
informational, not auto-fixed.

Ownership conflicts (more than one resolver stack actively listening on port 53) are
detected from real listener state, not inferred intent, and `plan()` refuses to run
while one is active.

```yaml
debkit:
  dns:
    enabled: false
    # Only "dnsmasq" is declaratively managed today. Any other value (or
    # empty) means "diagnose only, never touch anything."
    provider: dnsmasq
    # Rendered as `local=/<domain>/` + `domain=<domain>` per entry -- an
    # authoritative local zone, so lookups for it never leak upstream.
    local_domains: [dublinux.lan]
    # Rendered as `listen-address=<a>,<b>,...`.
    listen: ["127.0.0.1", "10.0.0.1"]
    # e.g. a local dnscrypt-proxy/similar. Empty means none declared.
    # Rendered as `server=<address>`.
    encrypted_upstream_address: "127.0.0.1:5053"
```

`verify()` includes a real functional `dig` lookup per declared local domain — a
genuine post-change functional test, not just "is dnsmasq active."
